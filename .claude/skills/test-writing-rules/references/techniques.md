# 技法カタログ

ケースを系統立てて出すための技法。観点（perspectives.md）が「何を見るか」、技法は「どう網羅するか」。例はこのリポジトリ（nepp-chan）の実テーブル・ルート・ツールに揃えている。

適用した技法はテスト名や `describe` の文章で表現する。`// 技法: 〇〇` のラベルコメントは冗長なので書かない。

## 同値分割

### 何をする
入力空間を「同じ振る舞いをするはずのクラス」に分割し、各クラスから代表値を 1 つずつ取る。

### 使い時
- 入力が連続値・列挙値・型クラスで分かれる場合
- 全部の値を試すとケースが爆発するが、クラス内なら同じ振る舞いが保証されるとき

### 例
```ts
// admin_users.role = "super_admin" | "admin" | "staff"
// 各ロールで requireRole の挙動を 1 ケースずつ
it("super_admin は全 admin ルートにアクセスできる", () => { ... });
it("admin は admin ルートにアクセスできる", () => { ... });
it("staff は admin ルートで 403 が返る", () => { ... });
```

### 注意
- クラス内の代表値選びは恣意的になりがち。境界値分析と併用する
- 「有効クラス」だけでなく **「無効クラス」**（型違い、値域外、未知の role 文字列）も忘れない

## 境界値分析

### 何をする
クラスの境界・端点を集中的に攻める。バグは境界に潜む。

### 攻める値（数値）
- `min - 1` / `min` / `min + 1`
- `max - 1` / `max` / `max + 1`
- `0` / `1` / `-1`
- `Number.MAX_SAFE_INTEGER` / `Number.MIN_SAFE_INTEGER`
- `Infinity` / `-Infinity` / `NaN`

### 攻める値（コレクション）
- 空配列 / 空文字 / `Set()` / `Map()`
- 1 要素 / 2 要素
- 1 ページ分ちょうど / 1 ページ + 1 件
- 最大長 / 最大長 + 1

### 攻める値（文字列）
- `""` / `" "`（空白のみ）
- ASCII 1 文字 / 多バイト 1 文字 / 絵文字 1 文字
- サロゲートペア境界（`"😀"` を 1 文字として扱えるか）
- broadcast 本文の最大長（LINE Messaging API の 5000 文字）

### 例
```ts
// /admin/broadcast の pagination 境界
it("ちょうど 1 ページ分のとき hasMore=false", () => { ... });
it("1 ページ + 1 件のとき hasMore=true", () => { ... });

// 投票選択肢の境界
it("choices が空配列のとき 400 を返す", () => { ... });
it("choices が 1 件のとき作成できる", () => { ... });
```

## デシジョンテーブル

### 何をする
複数の条件分岐がある場合、条件の組み合わせ表を作って網羅する。

### 例（resolvePrincipal）

| admin session | anonymous JWT | 期待される principal |
|---------------|---------------|----------------------|
| 有効          | 有効          | admin（session 優先）|
| 有効          | 無効/無し     | admin                |
| 無効/無し     | 有効          | anonymous            |
| 無効/無し     | 無効/無し     | null                 |

各行を 1 テストケースに展開。条件が多いとテーブルも巨大になるので **ペアワイズ** で削減する。

### 使い時
- if/else が 3 つ以上ネストしている関数（`requireRole` × principal 種別 × 期限切れ判定など）
- 条件と結果の対応表が仕様にある

## 状態遷移テスト

### 何をする
ステートマシン的な対象に対して、各状態・各遷移・**不正な遷移試行** を 1 ケースずつ書く。

### 攻めるべきもの
- 各状態で発火可能なイベントが期待通り遷移するか
- 不正な状態 → イベントの組み合わせで例外 / 無視 されるか
- 遷移時の副作用（log / event 発火 / `sent_at` などの timestamp 更新）が起きるか
- 過去の状態に戻る経路（戻り遷移）

### 例
```ts
// poll の status 遷移: draft → scheduled → sent → closed
it("draft の poll は send で sent になる", () => { ... });
it("sent の poll を再 send したら HTTPException(409) を投げる", () => { ... });
it("closed の poll を再 open する経路は無い", () => { ... });

// broadcast の status 遷移: draft → scheduled → sent / failed
it("scheduled の broadcast は cron で sent になる", () => { ... });
it("送信失敗時は failed になり error_message が記録される", () => { ... });
```

### 使い時
- broadcast / poll / admin_sessions / persona など status を持つドメイン
- 状態を表す型が union（`"draft" | "scheduled" | "sent" | "closed"`）になっているもの

## ペアワイズ（all-pairs）

### 何をする
パラメータが多い時、全組み合わせは爆発する（4 パラメータ × 各 3 値 = 81 ケース）。**「任意の 2 パラメータ間で全組み合わせを 1 度はカバーする」** で十分なバグを発見できるという経験則。

### 例
- `resolveModelTier({ intent, platform, isAdmin })` のような複数次元の決定関数: intent 2 値 × platform 3 値 × isAdmin 2 値 = 12 通りをペアワイズで 6 通り程度に削減
- ツール: PICT

### 使い時
- 設定オプション 4 つ以上の関数
- フォーム入力の組み合わせ
- API クエリパラメータ複数

## エラー推測

### 何をする
「開発者が忘れがちな入力」を意図的に攻める。観点チェックリスト（perspectives.md 軸 2）の補強と思えばよい。

### 攻めるネタ
- `null` / `undefined` / `NaN` / `Infinity`
- 空 / 巨大
- 古いタイムスタンプ / 未来のタイムスタンプ（`scheduled_at` が過去日時）
- 同時に呼ばれた場合（cron 重複起動）
- 文字エンコーディング（絵文字、サロゲートペア、合字）
- タイムゾーン境界 / DST 境界（`TZ=Asia/Tokyo` 前提を崩す入力）
- 権限不足 / トークン期限切れ（`admin_sessions.expires_at` が過去）
- ネットワーク失敗中 / 部分失敗（LINE 一斉配信で一部ユーザーが block 状態）

### 使い時
他の技法を当てた後、最後に「もっと意地悪な入力はないか」と一度立ち止まる。

## 技法の組み合わせ

実務では複数を併用する:

- **同値分割 + 境界値**: 各クラスの代表値 + 各クラス境界（最も一般的）
- **デシジョンテーブル + ペアワイズ**: 条件爆発を all-pairs で削減
- **状態遷移 + デシジョンテーブル**: 「状態 × イベント × ガード条件」の組み合わせ（poll の `status` × API 操作）
